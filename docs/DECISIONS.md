# Decision log

Why things are the way they are. Read before changing direction.

| # | Decision | Why |
|---|---|---|
| 1 | Build Splitcraft as the flagship portfolio project | Proves understanding of how Optimizely / AB Tasty work inside, the strongest interview story for a CRO developer. |
| 2 | Code editor, **no visual editor** in v1 | Matches real CRO dev work (custom JS/CSS). Visual editors break on dynamic sites and would add 2+ weeks. Can return as v2. |
| 3 | Use libraries for commodity parts, write the core yourself | Monaco (editor), Recharts (charts), Supabase (db/auth), a hash function are fine. Bucketing, targeting, anti-flicker, tracking, QA mode and stats choices must be your own code, because that is what interviews ask about. Never fork GrowthBook and rename it. |
| 4 | Workspace → Projects, not "Sites" | A project can be a site, a web app or a staging copy; it owns snippet, audiences, metrics, experiments. |
| 5 | Snippet must be installed for real tests | Same rule as every platform. Private previews on any site come later via a Chrome extension (v1.1). |
| 6 | No hardcoded tests | Everything is created from the dashboard; the SDK only reads config. |
| 7 | Targeting follows Who / Where / How / When | Industry model (AB Tasty). Segments persist, triggers are per visit; mixing both makes tricky audiences possible. |
| 8 | Nested ALL / ANY / NONE groups, plus custom JS condition | "Any tricky audience, not limited." |
| 9 | Metrics start from an event source | Same mental model as AB Tasty trackers and Optimizely events: clicks via CSS selector, everything else via JS / dataLayer / transaction. |
| 10 | Formula metric builder removed | Replaced by event-source builders. A "combine metrics" ratio option may come back. |
| 11 | Guardrails include Web Vitals | CRO developer angle: a variant that hurts LCP/CLS is not a win. |
| 12 | Honest statistics are a feature | Show uplift ranges, SRM, planned sample and "not ready yet" states; designs deliberately show a test that is ahead but not finished. |
| 13 | Auth = centered minimal card | Split-screen brand panel didn't feel right; top platforms (GrowthBook, Optimizely) use minimal centered login. |
| 14 | No fake logos, testimonials or customer numbers on the marketing site | Portfolio credibility. "Works with your stack" lists integrations as text only. |
| 15 | Brand | Ink `#15171A`, accent `#0F6B57`, variant B `#D97A2B` / `#F2B37A`, control `#3B5B8C`, ground `#F4F5F2`. Instrument Sans + JetBrains Mono. Logo = rounded square with a white and an orange bar. |
| 16 | QA panel ships as a separate file (`splitcraft-qa.iife.js`) | The main SDK has a tight size budget (see #17). The panel is only needed when `?splitcraft_force` is in the URL, so it loads on demand and normal visitors never download it. |
| 17 | SDK budget raised from 5 KB to 7 KB gzipped (QA panel: 3 KB, separate file) | The complete runtime (targeting context, sessions, page history, UTMs, source detection, tracking, anti-flicker) measured 6.46 KB. Hitting 5 KB meant dropping spec features such as page history or first-touch UTMs. 7 KB keeps every v1 feature with some headroom; CI enforces it. |
| 18 | Database tests run on PGlite, not Docker | PGlite is real Postgres in WebAssembly, installed from npm. Migrations, RLS policies and SQL functions are tested in Vitest locally and in CI without Docker. Supabase's `auth` schema and roles are stubbed in `supabase/tests/db.ts`; real auth is checked once deployed. |
| 19 | Pageview goals are matched in the browser in v1 | Storing every page view would make pageview metrics retroactive but multiply event volume against the 100k/month free tier. Retroactive pageview metrics can come in v1.1. |
| 20 | SDK events go through an Edge Function, not an insert-only policy | The function validates and trims each event, maps experiment keys to ids, rejects pages outside the project's domains and marks the project installed. The domain check stops accidental cross-site data, not deliberate forgery; any public-key analytics endpoint accepts forged events. |
| 21 | SDK budget raised from 7 KB to 8 KB gzipped; Web Vitals will load as a separate on-demand file | Click-through rate and time-to-first-click tracking took the main file to 6.9 KB, and dataLayer, transaction and browsing metrics still need room. 8 KB keeps them in the main file. Web Vitals code is only needed by experiments with a Web Vitals guardrail, so it loads on demand like the QA panel (#16). |
| 22 | Reach is estimated from one SDK ping per session | The SDK sends a `ping` on the first page of each session with device, screen width, source, session number and UTMs (no personal data). The dashboard samples up to 2,000 recent sessions and runs the targeting rules over them. Rules that need the live page (cookies, dataLayer, JS, page history, elements) can't be judged from a ping, so reach is shown as a range. Pages are judged by where the session started. Pings count toward the monthly event allowance: one per session, far fewer than storing every page view (#19). |
| 23 | Visitor country comes from a free lookup service (api.country.is) in the config endpoint | Supabase Edge Functions get no country header. The endpoint looks up the visitor's IP only when a live experiment has a country condition, with an 800 ms timeout and a one-hour in-memory cache; on failure the country is unknown rather than the page waiting. The IP goes to that service and is not stored. Those config responses are cached privately, not publicly. |
| 24 | Browsing and Web Vitals goals load from a separate on-demand bundle (`splitcraft-metrics.iife.js`, 2 KB budget) | Only experiments that use them need the code, so the main file stays under 8 KB (#21). Web Vitals use the browser's PerformanceObserver directly (no library) and are averaged per visitor rather than p75, so they get the same significance test as other value metrics. Browsing goals send an event per page while an experiment uses them, which counts toward the monthly allowance. |
| 25 | Previews on pages without the snippet use an opt-in bookmarklet (refines #5) | A per-project switch shows a "Splitcraft preview" bookmark that loads the SDK on the current page, so Preview on site works before the snippet is on every page. It only helps the person clicking it: real visitors still need the snippet. A dashboard can't add scripts to another site, so without a browser extension (v1.1) a bookmarklet is the only way; sites with a strict Content-Security-Policy block it. |
| 26 | Drafts are previewed with a secret per-experiment token | The config only serves live experiments, so a draft could never be previewed. "Preview on site" links now carry `splitcraft_preview=<token>`; the config endpoint then adds that experiment whatever its status, with no targeting and 100% traffic, and isn't cached. The token is a random UUID, so drafts stay private to people who have the link. Works with the snippet or the preview bookmark (#25). |
| 27 | Split URL and multivariate tests are in scope (reverses "multivariate tests" in the v1 out-of-scope list); dataLayer and purchase goals move to the on-demand metrics bundle, now 2.5 KB | Requested so the product matches how VWO offers A/B, split URL and MVT. Split URL needs a redirect in the SDK, which had 14 bytes left; moving dataLayer and transaction goal code into `splitcraft-metrics.iife.js` (#24) freed about 280 bytes, and that file's budget rises to 2.5 KB. MVT needs no SDK change: the dashboard generates one variant per combination (full factorial, max 16, equal weights) with the versions' code joined, and results add main effects per section. Split URL launch requires WHERE rules, so other pages never redirect. |
| 28 | The primary goal can change after launch (reverses "locks at launch" in PRODUCT_SPEC §3) | Requested: people pick the wrong goal, or learn what matters while a test runs. Results are computed from stored events, so they are recalculated for the new goal. The Goals step warns that goals not tracked before (clicks, custom events) only have data from the change on. Choosing the winning goal after seeing the numbers can overstate a win; the trade-off is left to the user. New metrics created from the Goals step are attached to the experiment (as primary if none is set, otherwise secondary) and return to it. |
| 29 | Preview anywhere uses a Chrome extension first, the bookmark second, and both get code straight from the dashboard (refines #5 and #25) | The bookmark alone often showed nothing: redirects dropped the preview parameters, it needed a per-project switch, and it only showed saved code. Now a separate preview bundle (`splitcraft-preview.iife.js`, 4 KB budget) applies the variants the dashboard sends, including unsaved edits. The Splitcraft Preview extension (`apps/extension`, loaded unpacked) injects it on every page load of the tab, runs variant JS through `chrome.userScripts` when allowed so a strict Content-Security-Policy can't block it, applies CSS edits in place and reloads for JS edits. The bookmark needs no install: it gets live edits from the dashboard tab that opened the page, or else the saved code named in the preview link, whose parameters are also in the hash so they survive redirects. The per-project "Preview on pages without the snippet" switch is gone; the bookmark is always offered in Preview on site. The snippet leaves an experiment alone while a preview owns it. |
| 30 | A visual (point-and-click) editor is in scope (reverses #2) | Requested on 2026-10-02 to close a gap with VWO, AB Tasty and Convert. It runs inside the on-site preview, so it works on any page the preview can reach: **Edit visually** in the preview panel lets you pick an element, rewrite its text, recolour it or hide it. The page sends only data (selector, kind, value) to the dashboard; the extension and the dashboard each check it, and the dashboard writes the variant code (text through `JSON.stringify`, colours only as `#rrggbb`, selectors without `{ } ; < >`). Nothing is saved until the user reviews the code and saves it, so a site can't slip code into a variant. The code editor stays the main tool for anything beyond simple changes. The preview bundle's budget rises from 4 KB to 6 KB; it is only loaded for the site owner, never for visitors. |
| 31 | Experiments can wait for activation, and the main bundle budget rises from 8 KB to 8.5 KB | Requested on 2026-10-07 to match Optimizely's activation types. Targeting gets an optional `activation`: when an element appears (watched with a MutationObserver, up to 60 s), when a JS condition becomes true (checked every 100 ms), or manually when the site calls `splitcraft.activate(key)`. Waiting experiments never hold the page hidden, and a route change cancels them. The bundle was 164 bytes from its limit, and this adds about 270, so the budget rises by 500 bytes; it is still small next to commercial snippets. |
